01 — 생각하는 방식

문제는 달라도, 푸는 순서는 같았습니다.

배포, 실시간 동기화, 파일 업로드, AI 응답 속도. 서로 다른 문제였지만 매번 같은 네 단계로 풀었습니다. 스크롤하면 오른쪽 파티클이 각 단계의 모양으로 바뀝니다.

  1. 01쪼갠다
  2. 02경계를 긋는다
  3. 03덜어낸다
  4. 04검증으로 닫는다

쪼갠다

“무중단 배포”는 고칠 수 없습니다. 고칠 수 있는 위협으로 쪼갭니다.

replica가 하나뿐인 폐쇄망에서 서비스를 죽이는 것은 컨테이너 교체의 몇 초가 아니었습니다. 신·구 버전이 같은 DB를 쓰는 순간의 스키마 비호환, 배포 중 스케줄러의 중복 실행과 공백, 파이프라인끼리의 간섭이었습니다. 세 위협을 각각 구조적으로 먼저 막고, 남은 HTTP 재기동 구간은 마지막에 제거했습니다.

  • SPOS 무중단 배포를 위협 3개 + 재기동 구간으로 분해
  • Malang 응답 지연을 호출 수 · 요청 단위 · 리전 왕복 · fallback으로 분해

경계를 긋는다

보장은 가장 단단한 층에. 규칙은 문서가 아니라 CI에.

“컨트롤러는 트랜잭션을 소유하지 않는다”, “도메인 판정 모듈은 DB·HTTP를 import하지 않는다” 같은 경계를 AST 구조 테스트로 만들었습니다. 사람이든 에이전트든 규칙을 어기면 리뷰 전에 파이프라인이 멈춥니다. 중복 업로드의 최종 방어선도 애플리케이션 코드가 아니라 DB의 부분 유니크 인덱스에 두었습니다.

  • SPOS AST 구조 테스트 · 게이트웨이 신뢰 경계(fail-closed) · 부분 유니크 인덱스
  • 갓생루팅 버튼 비활성화 대신 ref_id + DB UNIQUE

덜어낸다

가장 빠른 왕복은 하지 않는 왕복입니다.

부하 테스트에서 업로드의 약 25%가 실패한 원인은 요청마다 숨어 있던 키 조회 왕복이었습니다. 캐시와 single-flight로 동시 50개 요청의 조회를 1회로 묶었습니다. 같은 기준으로 Kafka 대신 이미 떠 있는 Redis를 쓰고, 필요가 증명되지 않은 전역 큐는 미뤘습니다.

  • SPOS 파일 핫패스의 숨은 왕복 제거 · Redis 전역 큐 보류
  • 테스트 콘솔 계획 선택 시 phase 요청 14회 → 3회
  • Malang slot 추출과 응답 생성을 single-call로

검증으로 닫는다

판정 불능은 성공이 아니라 실패입니다.

백엔드 앱의 배포 잡은 사흘 치 머지 내내 초록이었는데, 컨테이너에는 아무것도 반영되지 않았습니다. 그 뒤로 배포 성공의 정의를 “잡이 초록”에서 “서빙 중인 이미지 태그 = 머지 커밋 SHA”로 바꿨습니다. 모든 수정은 회귀 테스트로 봉인하고, 검증하지 못한 범위는 “미검증”이라고 보고합니다.

  • SPOS “무배포 green” 사고 → 타임아웃 hard-fail · 서빙 태그 실측
  • 갓생루팅 재실행 로그가 없는 성능 수치는 포트폴리오에서도 제외

사고 9건의 원인과 봉인 — 전체 기록 펼치기

로컬 실증은 메커니즘을 증명하지만, 실 호스트의 역사를 증명하지 않습니다. 사고 대부분은 신 체계의 결함이 아니라 compose 시절의 잔재(붙어 있던 컨테이너, 옛 이름을 참조하는 env, floating 태그, 상대경로)와 신 체계의 충돌이었습니다.

  • 판정 불능은 성공이 아니라 실패다. exit code 대신 UpdateStatus를 읽고, 최종 검증은 “서빙 중인 이미지 태그 = 머지 커밋 SHA”의 실측입니다.
  • 실패는 크게, 즉시. SEV1의 방아쇠는 거창한 설계 결함이 아니라 에러를 삼킨 한 줄이었습니다.
  • 수정은 인스턴스가 아니라 클래스에 건다. 같은 병리가 두 번 보이면 개별 패치가 아니라 술어 단위 진실표로 봉인합니다.
  • 좋은 readiness는 사고를 앞당겨 준다. DNS 결함이 프로덕션 업로드 실패가 아니라 배포 시점의 503으로 드러났습니다.

배포 벽시계는 Swarm 전환 후 ~9.5분까지 늘었다가, 마이그레이션을 one-shot 잡으로 단일화하고 배포 잡을 DAG로 병렬화해 ~2.5분으로 돌아왔습니다. 병렬화가 안전한 근거는 파이프라인 트릭이 아니라 “expand-only 마이그레이션”이라는 계약입니다.

CASE 02실시간 동기화

연결이 살아 있어도, 화면은 틀릴 수 있습니다

Redis Pub/Sub는 영속 로그가 아닙니다. 마지막 발행 하나만 유실되고 이후 변경이 없으면, 다음 이벤트의 번호 차이로도 누락을 알 수 없습니다. 그래서 이벤트 전달이 아니라 상태 수렴을 설계했습니다.

동기화 시뮬레이터 · power 채널
DB · 정본 r12 구간 A · 급전
Redis Pub/Sub checkpoint · 5초 (시연은 2.5초)
관제 화면 r12 구간 A · 급전 일치

‘다음 발행 유실’을 켜고 상태를 한 번만 바꿔 보세요. 그다음 checkpoint를 끄고 다시 해 보세요.

정본은 DB, Pub/Sub는 빠른 신호

같은 트랜잭션
업무 변경과 revision 증가를 같은 DB 트랜잭션에 반영합니다. 공개 상태가 실제로 바뀔 때만 revision이 오릅니다.
commit 후 발행
rollback된 변경은 알리지 않습니다. 발행 실패 때문에 이미 성공한 commit을 실패 응답으로 뒤집지도 않습니다.
공유 checkpoint
워커 안 구독자들이 타이머와 DB 조회 한 번을 공유합니다. 연결 수만큼 폴링하지 않으면서 마지막 유실까지 찾습니다.
첫 이벤트 = snapshot
구독 ACK 확인 → 한 read-only 트랜잭션에서 읽기 → 첫 SSE 이벤트로 전송. 최초 접속과 복구가 같은 경로가 됩니다.

주장하지 않는 것 exactly-once 전달, Last-Event-ID replay, 5초 내 복구 보장.

  • 실패한 연결을 정상처럼 유지하지 않는다. 연결별 큐 256 프레임 초과, Redis 재구독, checkpoint 오류는 일부 delta를 조용히 버리지 않고 연결 종료로 이어집니다.
  • 배열의 의미를 구분한다. snapshot의 빈 배열은 “전체가 비었음”, delta에서 항목 생략은 “기존 값 유지”입니다.
  • 운영일은 달력 날짜가 아니다. 계획 scope는 09:00~익일 09:00이고, 운영일이 바뀌면 resync 후 연결을 닫습니다. 같은 revision인데 조회 시각 때문에 내용이 달라지는 문제를 막습니다.
  • 15초 ping은 생존 신호일 뿐이다. 업무 상태 정합성의 증거로 쓰지 않습니다.

CASE 03재시도 · 멱등성

백오프는 중복 실행을 막지 않습니다

현장 앱이 0.5초 → 1초 → 2초 지수 백오프 재시도를 도입하자, 응답이 유실된 요청이 같은 업무를 다시 실행했습니다. 증빙과 스텝 이벤트가 중복으로 쌓이고, 결재 대기 건이 교체됐습니다. 요청 키를 새로 만들지 않고, 이미 있던 잠금과 도메인 상태로 풀었습니다.

    요청 UUID가 아니라 현재 도메인 상태로 판정

    이미 잡던 잠금
    제출 경로는 원래 계획 행을 FOR NO KEY UPDATE로 읽고 있었습니다. 그 잠금 안에서 완료 여부를 확인하므로 Redis 요청 키·advisory lock·요청 상태 테이블을 추가하지 않았습니다.
    가드의 위치
    권한 · 순서 · 반려 · 계약 검증 뒤 마지막에 둡니다. 기존 오류 우선순위를 바꾸지 않고, 지난 phase의 잘못된 재제출은 여전히 실패합니다.
    정정은 별도 경로
    내용을 바꾸려면 정정·수정 API를 씁니다. 멱등 가드는 “같은 제출인지”만 판단합니다.
    업로드 burst
    multipart 본문을 읽기 전에 수용 여부를 결정합니다. 워커당 동시 5 · 대기 85 · 최대 30초 FIFO, 초과 시 429 + 대기 깊이 기반 Retry-After.
    요청 유형별 서버 처리와 버린 대안 — 전체 기록 펼치기
    요청서버 처리
    같은 phase에서 이미 COMPLETED인 일반 스텝 재제출권한·순서·계약 검증 뒤, 증빙·이벤트 저장 본문을 실행하지 않고 완료 응답
    같은 사용자의 phase 재제출미결재 PENDING이 있고 이후 초안 변경이 없으면 현재 상태 반환. PENDING 교체 없음 — 그 사이 관제사가 결재해도 대상이 어긋나지 않음
    이미 지난 phase의 스텝 재제출기존 순서 검증 실패 유지. 멱등 가드로 무조건 200을 돌려주지 않음
    내용 정정별도 정정·수정 경로
    • 왜 Redis 전역 큐가 아닌가. 단일 호스트·다중 워커에서는 워커 로컬 제한만으로 메모리 가드를 유지할 수 있었습니다. lease·heartbeat 상태를 늘리지 않고, 워커 간 편중이 실측되면 다시 검토합니다.
    • 신호가 클라이언트까지 가는지 확인한다. 구현 리뷰에서 운영 예외 처리기가 Retry-After 헤더를 버리는 문제를 찾아 고치고, 운영 응답 경로를 회귀 테스트에 넣었습니다.
    • 주장 범위를 지킨다. 이 계약은 모든 POST의 exactly-once가 아니라 “현재 도메인 상태상 같은 제출인지”의 판정입니다. 목표 조건과 실측 성과를 구분해서 기록합니다.

    CASE 04파일 파이프라인 · 부하

    업로드의 25%가 정확히 +2.000초에 실패했습니다

    현장 증빙(사진·음성)은 서버 디스크에 평문으로 남으면 안 되고, 무결성은 감사 가능해야 했습니다. 클라이언트 봉투 암호화로 파이프라인을 만들었는데, 프론트 팀과의 동시 업로드 부하 테스트에서 약 25%가 503으로 떨어졌습니다.

    세 겹이 겹쳐 있었습니다

    1. 복호용 키는 캐시했지만, 응답 암호화용 활성 키는 매 요청 인증 서버로 HTTP 왕복을 했습니다. 캐시가 있다고 모든 경로가 캐시를 타지는 않았습니다.
    2. 그 왕복마다 HTTP 클라이언트를 새로 만들어 커넥션 풀 없이 TCP를 매번 새로 열었습니다.
    3. burst로 인증 서버의 accept 큐가 잠시 밀리면, 신규 connect들이 2초 타임아웃에서 일제히 죽었습니다.

    수정 활성 키에 TTL 캐시(60초) + single-flight, 모듈 공유 클라이언트로 커넥션 재사용(keepalive는 엣지 idle timeout보다 짧게), 게이트웨이 프록시도 앱 수명 공유 클라이언트로 전환. 스트리밍 응답의 정리 계약은 그대로 지켰습니다.

    서버가 평문을 저장하지 않는 업로드 설계 — 전체 기록 펼치기
    1. 클라이언트평문 sha256 계산 → AES-256-GCM 봉투 암호화. 봉투 헤더에 래핑된 키 메타와 nonce가 있어 파일 하나가 자기 완결적입니다.
    2. 파일 서버키 언래핑은 인증 서버에 위임합니다. 마스터키를 갖지 않으므로 파일 호스트가 통째로 털려도 저장된 암호문을 열 수 없습니다.
    3. 검증메모리에서만 복호 → 평문 해시 재계산·대조 → MIME 검증. 검증 순서는 값 객체 생성자가 단독 소유합니다(parse, don’t validate).
    4. 저장암호문 해시를 주소로 쓰는 content-addressed 저장, 임시 파일 → rename으로 원자적 쓰기. 중복의 최종 방어선은 DB 부분 유니크 인덱스입니다.
    5. 아카이브응답 경로 밖의 매시 배치가 원격 보관소로 전송 → 다시 읽어 해시 재검증 → 로컬 삭제. 다운로드 시 없으면 자동으로 되가져옵니다.
    해시대상역할
    checksum평문 sha256파일의 identity. 클라이언트가 선언해도 서버가 복호 후 다시 계산해 대조. 중복 업로드 판정 키
    blob sha256암호문 sha256저장 주소이자 아카이브 무결성 검증 키
    • 왜 BackgroundTasks가 아니라 배치인가. 요청에 붙인 백그라운드 작업은 배포·재시작 때 유실되고 재시도 이력이 남지 않습니다. 배치는 DB 장부를 보고 돌기 때문에 어떤 프로세스가 죽어도 다음 배치가 이어받습니다.
    • 교훈. 핫패스의 “요청당 1회 왕복”은 평시에는 몇 ms로 숨어 있다가 burst에서 connect 실패로 터집니다. 부하 최적화의 완료 정의도 “빨라진 것 같다”가 아니라 왕복 횟수를 세는 테스트와 재측정입니다.

    CASE 05상태 해석

    같은 계획을, 화면은 ‘대기 중’으로 알림은 ‘대상 아님’으로 읽었습니다

    등록 직후 계획에는 저장된 상태 snapshot이 없었습니다. 화면 조회는 이벤트·초안에서 상태를 복원했지만, 전원 변경 알림은 빈 snapshot을 그대로 판정해 계획을 뺐습니다. NULL 처리 한 줄이 아니라, 두 경로를 공통 상태 재료와 도메인 조립기로 수렴시켰습니다.

    운영일은 달력 날짜가 아닙니다 · KST 09:00 ~ 익일 09:00
    08:30–09:30

    작업 시작 < 운영일 종료 AND 작업 종료 > 운영일 시작

    공통 엔진을 쓴다고 대상 집합까지 같지는 않습니다. 화면은 완료·취소를 표시하고, 알림은 제외하고, 급전 안전 판정은 화면에 없는 전날 작업까지 포함합니다.

    04 — 에이전트와 일하는 방식

    에이전트의 품질은 프롬프트가 아니라 저장소가 결정합니다.

    SPOS의 상당 부분을 Claude Code·Codex와 함께 구현했습니다. 배운 것은 도구 사용법이 아니라 프로세스 설계였습니다. 에이전트는 그럴듯하지만 틀린 코드를 자신 있게 씁니다. 그래서 계약 · 가드레일 · 검증 루프를 저장소에 심었습니다.

    두 번 일하지 않는 순서

    1. 계약 확정API · 권한 · UX의 미결정 사항을 구현 전에 인터뷰로 확정합니다. 공백을 남기면 에이전트는 그럴듯한 추측으로 메웁니다.
    2. 흐름표요청 → 권한·lock → DB 변경 → side effect → 응답·에러를 한글 의사코드로 씁니다. 코드가 아니라 의사코드 단계에서 이해를 검증합니다.
    3. 영향 조사호출자 전체, read·write path, 스케줄러·알림·캐시·트랜잭션 side effect. 같은 상태 기준을 쓰는 형제 경로를 함께 고칩니다.
    4. 실패 테스트 먼저“다 됐습니다”를 믿는 대신 빨간 테스트가 초록이 되는 것을 봅니다.
    5. 구현 · 스모크실제로 띄운 서버에 시나리오 테스트로 프론트의 호출 순서를 재연합니다.
    6. 검증 보고실행한 명령 · 결과 · 미검증 범위. 검증하지 못한 것은 “해결됨”이 아니라 “미검증”입니다.

    실제로 레버리지가 있었던 순서

    1. 어기면 CI가 막는 가드레일구조 테스트 · 마이그레이션 정책 테스트
    2. 구현 전 의사코드 · 계약 승인싼 단계에서의 검증
    3. source of truth 단일화이슈 · 커밋 · Swagger · 런북
    4. 실측 기반 완료 정의스모크 결과 없는 “완료”는 완료가 아님
    5. 프롬프트 요령위 넷이 갖춰진 뒤에야 의미가 있었음
    • 저장소 = 에이전트의 온보딩 문서 에이전트는 세션마다 기억이 리셋됩니다. CLAUDE.md(프로젝트 헌법) · 런북(알려진 장애와 절차) · 용어집 + ADR을 저장소에 두자, 지시가 “이 파일 고쳐줘”에서 “이 이슈 구현해줘”로 올라갔습니다.
    • 역할 분담과 격리 계획 · 설계 · 리뷰는 상위 모델, 대량 구현은 서브에이전트에 맡깁니다. 넓은 조사는 읽기 전용 에이전트를 병렬로 펼치고, 병렬 구현은 git worktree로 격리합니다. 사람의 역할은 “계약 결정자 + 검증자”입니다.
    • 이슈가 위임 단위 GitLab Issues가 스펙과 진행도의 유일한 정본입니다. In Progress 라벨이 곧 잠금이고, 큰 결정은 map → 조사 → 결정 잠금 → SPEC → phase 티켓으로 쪼갭니다. 범위와 완료 조건이 이슈에 있어야 위임이 안전합니다.
    • 출력도 규칙으로 에이전트 보고에 한국어 간단 기술 문서(STE) 규칙과 프로젝트 승인 용어표를 적용합니다. 한 개념에 한 단어, 첫 줄은 결과. 라이브러리는 최신 문서(Context7)를 먼저 확인하고, 화면은 Playwright로 직접 봅니다.

    이 저장소의 규칙 대부분은 사고의 화석입니다

    사고남긴 규칙과 장치
    스냅샷 마이그레이션이 신규 환경 빌드를 깨뜨림체인을 pg_dump baseline으로 스쿼시 + create_all 전면 금지 테스트 + 일회용 Postgres 실측

    git clean이 시크릿 마운트를 삭제clean 예외 + 시크릿 주입 실패 시 fail-fast
    pgbouncer·asyncpg 충돌, 커넥션 슬롯 고갈pgbouncer 경유 강제 + 접속 설정 표준화, 설정 테스트로 봉인
    신규 API의 프록시 등록 누락으로 404라우터 등록 + 프록시 spec + 실호출 검증을 한 세트로
    같은 판정 지식 3벌 복제로 drift“2벌째가 개입 시점” + 진실표 단일 소유 + AST 재선언 탐지
