## 2. 프로젝트 개요

갓생루팅은 모임 구성원이 미션 성공/실패에 따라 벌금과 상금을 정산하는 협업 서비스입니다. GPS/사진 기반 미션 인증, 카카오 초대 링크, 팀별 배팅, 정산 캘린더/갤러리 같은 제품 기능이 있었고, 백엔드는 Spring Boot, MySQL, Redis, Kafka를 사용했습니다.

제품 전체 기능보다 Java/Spring 기반 신뢰성 설계가 드러나는 정산 흐름을 중심으로 정리했습니다.

## 4. 문제 해결 사례

### 문제 1. 이체 요청 중복 처리

**상황**
사용자가 정산 버튼을 빠르게 여러 번 누르거나 네트워크 재전송이 발생하면 같은 의도의 이체가 여러 번 들어올 수 있습니다. 프론트엔드 버튼 비활성화만으로는 API 재시도, 다른 클라이언트, 장애 복구 상황을 충분히 막을 수 없습니다.

**선택**
거래 요청마다 `ref_id`를 두고 DB Unique 제약을 적용했습니다. Redis 캐시 키도 후보였지만, 돈처럼 취급되는 상태에서는 TTL 관리보다 영속 저장소의 제약이 더 설명하기 쉽고 안정적이라고 판단했습니다.

**설명 가능한 코드 수준**

```java
@Column(nullable = false, unique = true)
private String refId;
```

**정리한 결과**
중복 요청을 “성공처럼 한 번만 반영”하거나 “이미 처리된 요청으로 응답”하는 멱등 처리 방향을 설계했습니다. 최신 테스트 로그가 없는 운영 무결성 수치는 제외했습니다.

### 문제 2. 잔액 업데이트 동시성 충돌

**상황**
여러 사용자의 정산이 같은 계좌 잔액을 동시에 변경하면 lost update나 잔액 불일치가 발생할 수 있습니다.

**선택**
서비스 트래픽이 낮고 단일 DB를 사용한 프로젝트였기 때문에 비관적 락을 선택했습니다. 낙관적 락의 재시도 설계보다, 정산 흐름에서는 먼저 일관성을 확보하는 편이 적절하다고 봤습니다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Account findByIdForUpdate(Long id);
```

**정리한 결과**
락 대기 시간이 생길 수 있지만, 같은 계좌의 잔액 변경을 순서화해 데이터 일관성을 지키는 구조를 만들었습니다. 재실행 가능한 부하 테스트 로그가 없는 특정 처리 시간 수치는 제외했습니다.

### 문제 3. 부분 성공으로 인한 잔액 불일치

**상황**
출금은 성공했는데 입금이나 거래 기록 저장이 실패하면 총액이 맞지 않는 상태가 남습니다.

**선택**
차감, 입금, 거래 기록 생성을 하나의 `@Transactional` 경계 안에 두었습니다. 단일 DB 프로젝트라서 SAGA 같은 보상 트랜잭션 패턴은 규모 대비 복잡하다고 판단했습니다.

```java
@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount, String refId) {
    Account from = accountRepository.findByIdForUpdate(fromId);
    Account to = accountRepository.findByIdForUpdate(toId);

    from.withdraw(amount);
    to.deposit(amount);

    transactionRepository.save(Transaction.of(from, to, amount, refId));
}
```

**정리한 결과**
정산 도메인에서 트랜잭션 경계를 어디에 둘지, 어떤 실패를 한 단위로 rollback할지 정리했습니다.

## 5. 인증, 배포, 운영 보조 경험

- **인증/인가:** JWT와 HttpOnly Cookie 기반 인증, 그룹/미션 접근 권한 검사를 구성했습니다.
- **입력 검증:** DTO 단위 validation으로 잘못된 요청이 서비스 계층으로 들어오기 전에 차단했습니다.
- **캐싱/락:** Redis를 캐시와 정산 실행 중복 방지 용도로 사용했습니다.
- **비동기 알림:** Kafka 이벤트로 알림 처리를 핵심 정산 경로와 분리했습니다.
- **배포:** AWS EC2, Nginx, Docker, Jenkins 기반 배포 흐름을 경험했습니다.
