## 2. 프로젝트 개요

Malang은 한일 커플/언어교환 사용자를 위한 모바일 앱과 내부 Admin이 공유하는 AI 서비스 백엔드입니다. 사용자는 상황별 대화 연습, 음성 입력, AI 응답, 구독 플랜별 기능 차이를 경험합니다. 백엔드는 NestJS와 Prisma/PostgreSQL 기반이며, OpenAI, Vertex/Gemini, ElevenLabs, Firebase App Check/FCM, S3-compatible storage를 연동합니다.

핵심은 AI API 호출 자체가 아니라, AI 기능을 제품 백엔드의 상태, 권한, 응답 속도, 실패 처리, 검증 흐름으로 정리한 점입니다.

## 3. 응답 속도 개선 과정 <span id="speed"></span>

### 문제. 한 번의 대화 turn 안에 여러 왕복이 쌓임

AI 대화는 사용자가 한 문장을 보낸 뒤 바로 답을 기대하는 흐름입니다. 그런데 초기 구조에서는 branch 판단, slot 추출, agent 응답 생성, provider 호출이 순차로 이어지면서 사용자가 기다리는 시간이 길어질 수 있었습니다. 특히 도메인 답변에 필요한 정보가 이미 정해져 있는데도 매번 모델 판단을 거치면 지연과 비용이 함께 커집니다.

### 진단. 병목을 네 가지로 분리

<div className="portfolio-proof-list">
  <strong>모델 호출 수</strong><span>한 turn 안에서 branch 판단, slot 추출, 응답 생성이 각각 호출되는지 확인했습니다.</span>
  <strong>요청 단위</strong><span>slot 추출과 답변 생성에 필요한 정보를 같은 요청으로 묶을 수 있는지 나눠 봤습니다.</span>
  <strong>리전 왕복</strong><span>백엔드와 provider 호출 경로가 멀리 돌아가며 지연을 키우는지 점검했습니다.</span>
  <strong>fallback 경로</strong><span>속도 개선 중에도 정보 질문, slot 수집, 실패 응답이 깨지지 않는지 reason code로 구분했습니다.</span>
</div>

### 해결 1. 확정 가능한 분기는 모델 호출 없이 처리

RULE 평가만으로 다음 단계가 결정되는 branch는 LLM에게 다시 묻지 않도록 deterministic bypass를 정리했습니다. 예를 들어 사용자의 선택지가 이미 workflow rule 안에서 확정되는 경우에는 모델 판단보다 서버 규칙을 우선했습니다. 이 방식은 응답 지연을 줄이는 동시에 같은 입력이 같은 경로로 처리되도록 만들어 디버깅도 쉬워집니다.

### 해결 2. slot 추출과 응답 생성을 한 요청으로 묶음

도메인상 필요한 slot과 응답 형식이 정해져 있는 경로에서는 slot 추출 결과를 받은 뒤 다시 응답 생성을 호출하는 대신, 필요한 정보를 한 provider 요청에 담는 single-call 경로를 정리했습니다. 이 변경은 “모델이 할 일”을 줄인 것이 아니라, 모델에게 전달하는 작업 단위를 제품 흐름에 맞게 다시 묶은 것입니다.

### 해결 3. provider 호출 리전을 가까운 권역으로 정렬

응답 지연에는 코드 내부 처리뿐 아니라 네트워크 왕복도 영향을 줍니다. 백엔드와 AI provider 호출 경로가 불필요하게 멀리 돌아가지 않도록 리전 구성을 점검하고, 가까운 권역으로 맞추는 변경을 적용했습니다. 모델 성능 수치보다 사용자 요청이 provider까지 이동하고 돌아오는 경로를 짧게 만드는 백엔드 관점의 개선입니다.

### 검증. 속도와 대화 품질을 함께 확인

속도만 빠르게 만드는 변경은 실제 대화 품질을 깨뜨릴 수 있습니다. 그래서 identity 질문, 영업시간/메뉴 같은 정보 질문, slot 수집 중 끼어드는 질문, fallback이 필요한 경로를 테스트로 묶었습니다. 응답 지연을 줄이는 변경이 대화 의미와 action semantics를 망가뜨리지 않는지 함께 봤습니다.
